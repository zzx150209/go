完成编辑、编译、运行和调试，判断常见程序错误。

检索词：IDE编译调试

本课先记住

  • 核心结论： IDE 把编辑、保存、编译、运行和调试工具放在一起，但每一步仍有独立结果；修改源码后必须保存并重新编译，运行结果才来自新版本。

知识范围与官方定位

本页对应 GESP C++ 一级大纲中的“集成开发环境”。这里不要求记住某一款软件的所有按钮，而是要学会一套换到其他 IDE 也能使用的工作方法。

学完本页，你应当能回答三个问题：

  1. IDE 的各个区域分别在处理什么？
  2. 编辑、保存、编译和运行为什么不能互相代替？
  3. 程序出错时，怎样根据现象找到下一步检查位置？

上一页已经介绍过源文件和可执行程序：源文件保存人写的 C++ 代码，可执行程序是编译器翻译后的结果。本页把它们放进一次真实的开发过程。下一页再具体学习 C++ 程序由哪些部分组成。

01 编辑与保存

IDE 把开发工具放在同一个环境里

IDE 是 Integrated Development Environment 的缩写，中文叫“集成开发环境”。“集成”的意思是：它把编写、编译、运行和调试程序时常用的工具集中在一个界面里，让我们不用频繁切换软件。

常见 IDE 通常包含下面几个区域。不同软件的名称和位置可能不同，但它们承担的工作相近。

常见区域 主要作用 在哪里找证据
文件或项目区 查看、新建和切换源文件 文件名、文件夹位置、.cpp 后缀
代码编辑区 输入和修改源代码 光标所在行、行号、尚未保存的修改标记
编译信息区 显示编译是否成功以及错误信息 第一条错误、行号、错误附近的提示
运行窗口或终端 向程序输入数据，查看实际输出 输入内容、输出内容、程序是否正常结束
调试区 暂停程序并观察变量等运行状态 当前执行位置、变量当时的值

IDE 只是把工具放到了一起，并没有把几个动作变成同一件事。按下“保存”不会自动证明程序正确；看到编辑器里有新代码，也不代表正在运行的已经是新版本。

编辑状态和磁盘文件不是同一个状态

在编辑器里敲下文字，先改变的是编辑区中的内容。执行保存后，这些内容才写入磁盘中的 .cpp 源文件。

可以把它理解成写作业：

  • 编辑，是在草稿上改字；
  • 保存，是把当前内容正式写进文件；
  • 编译，是让编译器读取文件并检查、翻译；
  • 运行，是执行最近一次成功编译得到的程序。

这四步处理的对象不同：

动作 主要处理什么 成功后得到什么 不能代替什么
编辑 编辑器中的代码文字 一次尚待保存的修改 不能代替保存
保存 当前编辑内容 磁盘中的最新源文件 不能检查程序逻辑
编译 已保存的源文件 新的可执行程序，或编译错误 不能证明答案正确
运行 最近一次成功编译的可执行程序 实际输出或运行现象 不能自动修改源代码

为什么改了代码，结果却可能没变

假设 answer.cpp 原来会输出 3。你在编辑器中把它改成输出 5，却忘了保存。编译器读取磁盘时，看到的仍可能是旧文件，于是新编译的程序仍输出 3。

还有另一种情况：你已经保存，却没有重新编译，直接运行了旧的可执行程序，结果也可能还是 3。

所以，“代码明明改了，结果怎么没变”不能只盯着代码。先检查这两个问题：

  1. 修改是否已经保存到源文件？
  2. 保存后是否重新编译成功？

02 编译

编译器做了什么

编译器读取源代码，检查它是否符合 C++ 的规则，并把能够通过检查的代码翻译成可执行程序。

已保存的 .cpp 源文件          ↓ 编译器读取、检查和翻译编译成功：得到新的可执行程序编译失败：得到错误信息，不会得到这次的新程序

编译失败时，旧的可执行程序可能还留在电脑里。此时如果 IDE 仍允许运行，你看到的可能是旧版本结果。因此，不能把“运行窗口弹出来了”误当成“刚才的修改已经编译成功”。

C++ 主要采用“先编译，再运行”的方式。有些语言会使用解释器边读取边执行；一级只需知道两者的基本区别，不需要研究解释器内部怎样工作。

怎样阅读编译错误

少写分号、括号不配对、名字拼错、使用没有定义的变量，都可能让编译失败。面对多条报错时，可以按这个顺序检查：

  1. 先确认编译的是自己刚刚保存的文件。
  2. 从第一条错误开始看，不要急着追最后一条。
  3. 根据提示找到对应行，同时检查它的上一行。
  4. 只修正一个明确的问题，再重新编译。

为什么还要看上一行？编译器按顺序读取代码。有时上一行已经出错，但它读到下一行时才确定前面的结构无法成立。

下面只观察“漏写分号”怎样影响编译，不要求现在掌握两条语句的完整含义：

int number = 3cout << number << endl;

第一行末尾缺少 ;。编译器可能在读取第二行时才报告错误，所以提示位置不一定就是真正需要修改的位置。正确写法是：

int number = 3;cout << number << endl;

语句、分号和完整程序结构会在下一页详细学习。本页先记住：错误提示是线索，不是替你直接给出的答案。

编译成功说明了什么

编译成功说明编译器没有发现阻止本次翻译继续进行的错误，并且生成了新的可执行程序。它不保证：

  • 计算公式符合题意；
  • 所有输入都能得到正确答案；
  • 输出的空格、换行和小数位数符合要求；
  • 程序运行时一定不会出现问题。

因此，编译成功只是进入运行验证的起点。

03 运行与重新编译

运行的是可执行程序

运行时，操作系统加载最近一次成功编译得到的可执行程序。程序再按代码规定读取输入、进行计算并产生输出。

这里有一条很重要的版本关系：

源文件版本 A ──编译成功──→ 可执行程序版本 A源文件改成版本 B ──只保存──→ 可执行程序仍是版本 A源文件版本 B ──重新编译成功──→ 可执行程序才变成版本 B

假设旧程序计算 3 + 4，输出 7。你把运算改成乘法并保存，但没有重新编译，运行的仍是旧可执行程序，所以仍可能输出 7。只有重新编译成功后，新程序才会输出 12。

这正是修改代码后必须重复“保存 → 编译 → 运行”的原因。

运行时要保存三份证据

验证程序时，不要只记一句“好像不对”。至少记录：

证据 要记录什么 有什么用
本次输入 实际输入的每一个数据 保证能够重复同一次测试
期望输出 根据题意手算的正确结果 给实际输出一个判断标准
实际输出 程序真正显示的内容 判断数值和格式哪里不一致

例如，任务要求输入两个整数并输出它们的和：

输入：3 4期望输出：7实际输出：12

只看 12，无法判断它为什么错；把输入和期望结果放在旁边，就能提出更具体的检查方向：程序是否误做了乘法？两个输入变量是否读反或被改动？

重新编译前后怎样确认版本

每次修改后都执行同一条短流程：

修改代码 → 保存文件 → 重新编译       → 确认编译成功 → 用同一组输入运行 → 对照期望输出

如果编译失败，就先处理编译错误，不要拿旧程序的运行结果判断刚才的修改。只有出现“本次编译成功”的证据，运行结果才属于当前源代码。

04 错误类型与调试

先按现象判断错误发生在哪个阶段

程序出错时，先判断它停在“编译前、运行中，还是结果核对”哪个阶段。分类的目的不是背名称，而是缩小检查范围。

错误类型 常见现象 首先检查 一个边界提醒
编译错误 本次编译失败，没有生成新程序 第一条错误、错误行和上一行、分号、括号、拼写、变量定义 后面的多条错误可能由第一处错误连带产生
运行错误 已经开始运行，但异常结束或长时间不能结束 输入是否符合要求、除数是否可能为 0、循环能否结束 除以 0 等问题的具体表现可能因环境而异
逻辑错误 程序正常结束，但计算结果不符合题意 公式、条件、执行顺序、变量变化、边界情况 编译器通常不知道题目真正要求什么
格式错误 主要数值可能正确，但输出形式不符合要求 多余文字、空格、换行、小数位数 给人看着相近，不代表在线评测认为相同

同一个现象背后可能有不止一个原因。例如“没有看到结果”，既可能是程序还在等待输入，也可能是循环没有结束，还可能是程序异常终止。调试时要继续收集证据，不能只凭第一感觉下结论。

WA 不是一种编译错误

在线评测中的 WA（Wrong Answer，答案错误） 表示程序已经运行并提交了输出，但输出没有通过评测。它是评测结果，不是 C++ 编译器给出的语法错误名称。

WA 常见原因包括：

  • 公式或条件写错，属于逻辑问题；
  • 漏考虑 0、相等值等边界情况；
  • 输入理解错误；
  • 输出了多余提示文字，或空格、换行不符合要求。

遇到 WA 时，应回到具体失败数据，比较“输入—期望输出—实际输出”，而不是再次盲目点击编译。

05 调试方法

调试不是随便改代码

调试是根据现象收集证据、提出原因、修改并重新验证的过程。一级常用的方法有：

  1. 用简单数据手算期望结果。
  2. 逐步记录关键变量的变化。
  3. 在关键位置临时输出变量值。
  4. 检查 0、1、相等值和临界值等边界数据。
  5. 修正后保存、重新编译，再用原数据复查。

调试按钮只是工具之一。即使暂时不会使用断点和变量窗口，也能通过手算、变量记录和临时输出来定位许多一级程序的问题。

从假设到验证，一次只检查一件事

仍看这个现象：输入 3 4，期望输出 7，实际输出 12。

可以按下面的顺序调查：

步骤 操作 得到的证据或结论
1 手算 3 + 4 期望结果确实是 7
2 确认本次输入 两个输入分别是 3 和 4
3 观察输入变量 变量中保存的也是 3 和 4
4 检查运算表达式 发现误把加法写成乘法，3 × 4 正好是 12
5 只修正这个运算符 修改目标明确，不同时改无关代码
6 保存并重新编译 生成包含修正的新程序
7 再用 3 4 运行 实际输出变为 7，与期望相同
8 再测 0 5 实际输出应为 5，补充检查边界情况

这个过程比“看到错就同时改很多行”可靠。一次修改太多，即使结果碰巧正确，也很难知道真正起作用的是哪一处。

临时输出用完要清理

为了观察变量，可以暂时把变量值输出到运行窗口。但这些文字也会成为程序实际输出的一部分。

如果题目只要求输出一个答案，提交时却多了一行“当前变量是……”，在线评测可能给出 WA。因此：

  1. 调试时用临时输出收集证据；
  2. 确认原因并修正；
  3. 删除临时输出；
  4. 重新编译；
  5. 最后按题目格式再运行一次。

注释的具体写法会在下一页“程序基本结构”中讲解。现在只需知道，调试信息不能混进最终答案。

第一次开发的完整闭环

第一次独立编写程序时，可以照着下面的顺序操作。它既包含成功路线，也包含出错后的返回路线。

顺序 要做什么 通过什么证据继续
1 新建或打开正确的 .cpp 文件 文件名、保存位置和后缀正确
2 在编辑区输入或修改代码 修改内容与当前任务一致
3 保存源文件 未保存标记消失，磁盘中是最新版本
4 执行编译 明确看到本次编译成功或第一条错误
5A 如果编译失败，检查第一条错误及其附近 修正后回到第 3 步
5B 如果编译成功，运行新程序 运行窗口开始接收输入或显示输出
6 输入自己记录好的测试数据 输入数量和顺序符合任务要求
7 比较期望输出与实际输出 完全相同则继续测其他数据，不同则进入调试
8 根据错误类型收集证据并只修正明确问题 修正后回到第 3 步，重新走完整闭环

可以把它压缩成一句操作口令：

改完先保存，保存后编译，编译成功再运行；结果不对留证据，修正以后从保存重新开始。

知识点速查表

看到的现象 先判断什么 下一步
编辑区有新内容，运行结果没变 是否忘记保存 保存后重新编译
已保存，但仍是旧结果 是否运行了旧可执行程序 确认本次重新编译成功
出现许多编译错误 第一条错误是否引发后续错误 查第一条错误、当前行和上一行
能运行，但答案数值不对 逻辑或边界是否错误 手算期望值，记录变量变化
数值正确却评测不通过 输出格式是否精确匹配 删除提示文字，检查空格和换行
调试后本地正确，提交仍错 临时输出是否还在 清理后重新编译、复查

典型例题

小灯完成了一个“输入两个整数，输出它们的和”的程序。他输入 3 4，程序成功编译并正常结束，但输出是 12。他应该怎样判断和处理？

分析：

  1. 编译已经成功，所以这不是编译错误。
  2. 程序能正常结束，却没有得到题目要求的 7，首先判断为逻辑错误。
  3. 记录输入 3 4、期望输出 7、实际输出 12。
  4. 检查输入变量后，继续检查运算表达式；12 与 3 × 4 相符，很可能把加法误写成了乘法。
  5. 修正后要保存、重新编译，并再次用 3 4 验证，不能直接运行旧程序。
  6. 再用 0 5 等数据复查，确认结果仍符合题意。

结论：判断错误类型只是起点，真正完成调试还要找到证据、修正原因并重新验证。

引导练习（不记录进度）

把程序输出从 Hello 改成 Hi，运行后仍看到 Hello。按顺序检查：编辑区是否已保存、本次编译是否成功、运行的可执行程序是否来自本次编译。每完成一步只记录一个结论，不同时随机改代码。

成功标准： 最终运行结果必须是 Hi，并能指出旧结果出现在哪一步。随后不看提示独立完成页末“整页综合测试”；提交后根据解析把每个错误归入编辑/保存、编译、运行、逻辑或格式阶段。

常见错误

把 IDE 当成会自动完成一切的工具

错误做法： 代码改完后直接看运行结果，默认 IDE 已经保存和重新编译。

为什么错： 编辑、保存、编译、运行分别处理不同对象，具体 IDE 的自动行为也可能不同。

怎样检查： 主动执行保存和编译，并确认本次编译成功后再运行。

从最后一条编译错误开始修改

错误做法： 看到十几条错误，从列表最下面逐条修改。

为什么错： 第一处结构错误可能让编译器误解后续代码，从而产生连带提示。

怎样检查： 从第一条错误开始，同时看错误行和上一行；修正后重新编译，观察其余提示是否消失。

只凭“能运行”判断程序正确

错误做法： 程序没有报错就立即提交。

为什么错： 逻辑错误和格式错误不会一定阻止程序运行。

怎样检查： 先手算期望输出，再用普通数据和边界数据比较实际结果。

随机同时改很多处

错误做法： 不记录输入和现象，一次修改多个变量、公式和输出语句。

为什么错： 即使结果变化，也无法确认哪一处是根因，还可能引入新错误。

怎样检查： 根据证据提出一个具体原因，一次只修正与它有关的位置，再用同一组数据复查。

忘记删除调试输出

错误做法： 调试时输出了变量值，提交前没有清理。

为什么错： 在线评测会把调试文字也当作正式答案的一部分。

怎样检查： 清理临时输出，重新编译，再逐字核对最终输出格式。

8 题

第 1 题在集成开发环境中，把 C++ 源代码转换成可执行程序的过程称为什么？

答案：A
编译器检查源代码并把它转换为计算机能够执行的程序。
对应知识点：02 编译

第 2 题程序编译时提示少写了分号，这类问题属于什么错误？

答案：A
分号缺失不符合 C++ 语法规则，编译器通常会报告语法错误。
对应知识点：04 错误类型与调试

第 3 题程序能够成功编译，但运行结果不符合题意，下一步最适合做什么？

答案：A
成功编译只说明语法基本通过；结果错误时应结合样例检查算法、条件和变量变化。
对应知识点：03 运行与重新编译

第 4 题修改源代码后，要让新的修改体现在运行结果中，通常需要先做什么？

答案：A
修改后的源代码需要重新编译，生成新的可执行程序后再运行。
对应知识点：01 编辑与保存

第 5 题下面哪一行是合法的 C++ 单行注释？

答案：A
C++ 使用 // 表示从当前位置到行末的单行注释。
对应知识点：05 调试方法

第 6 题下面哪种写法是合法的 C++ 多行注释？

答案：A
C++ 使用 /* 开始、*/ 结束多行注释，注释内容可以跨越多行。
对应知识点：05 调试方法

第 7 题程序能够编译并正常结束，但输出的答案不符合题意，这通常属于哪类错误？

答案：C
语法通过且程序能运行，但计算过程或条件设计有误，通常属于逻辑错误；若数值正确但空格、换行不符，则属于格式错误。
对应知识点：04 错误类型与调试

第 8 题为了检查变量 sum 的变化，临时加入 cout << sum << endl;。程序确认正确后，提交前应怎么做？

答案：A
临时输出能帮助观察变量，但会改变最终输出格式；确认问题解决后应删除或注释掉，再用样例复查正式输出。
对应知识点：05 调试方法
